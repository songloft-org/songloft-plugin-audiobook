# 音频文件传输方案对比分析

## 背景

有声书插件当前通过 `songloft.fs.readFile(path, { encoding: 'base64' })` 读取 MP3 文件，base64 编码后通过 JSON 返回给前端播放。本文对比当前方案与"宿主直接 serve 文件"的优劣。

---

## 两种方案流程

### 方案 A（当前）：base64 整文件搬运

```
前端 GET /api/books/:id/chapters/:chapterId/audio
  → QuickJS: songloft.fs.readFile(path, { encoding: 'base64' })
    → Go 读磁盘 → base64 编码 → 返回字符串
  → JSON 包装: { audio: "SGVsbG8gV29ybGQ..." }
  → 前端 atob() → Uint8Array → Blob → Object URL → <audio src="blob:...">
```

### 方案 B（推荐）：宿主直接 serve 文件

```
前端 GET /api/books/:id/chapters/:chapterId/audio
  → 插件返回: { url: "/api/v1/jsplugin/audiobook/data/xxx.mp3" }
  → 前端 <audio src="url">
    → 浏览器发起 GET，带 Range 头
    → Go HTTP handler 读磁盘，支持 206 Partial Content
```

---

## 开销对比（以 17MB MP3 章节为例）

### 方案 A 各环节开销

| 环节 | 数据量 | 备注 |
|------|--------|------|
| Go 读磁盘 | 17 MB | 正常 |
| base64 编码 | 17 MB → 23 MB | 膨胀 33% |
| QuickJS 字符串驻留 | 23 MB | 占 JS 堆内存 |
| JSON 序列化 | 23 MB | 额外转义开销 |
| HTTP 响应体 | ~23 MB | 无压缩时为纯文本 |
| 前端 atob 解码 | 23 MB → 17 MB | 阻塞主线程 |
| 前端 Blob 构建 | 17 MB | 内存常驻直到页面关闭 |

### 方案 B 各环节开销

| 环节 | 数据量 | 备注 |
|------|--------|------|
| QuickJS 响应 | ~200 bytes | 仅 JSON `{ url: "..." }` |
| HTTP 传输 | 17 MB | 原生二进制 |
| 浏览器处理 | 按需缓冲 | Range 请求只取需要的片段 |

---

## 关键差异逐项对比

### 1. Range 请求（拖动进度条）

| | 方案 A | 方案 B |
|---|---|---|
| 实现 | 不支持 | 原生支持 `Range` + `206 Partial Content` |
| 拖进度条 | 必须全文件下载完才能跳转 | 秒拖，浏览器按 Range 取对应段 |
| Go 实现 | — | `http.ServeContent` 一行搞定 |

方案 A 中整个音频是一个 `blob:` URL，浏览器无法发起 Range 请求，`<audio>` 拖动进度条不会生效，直到整个文件下载完毕。

### 2. 内存占用

| | 方案 A | 方案 B |
|---|---|---|
| QuickJS 堆 | 文件大小 × 2-3（base64 字符串 + JSON 序列化缓冲区） | ~200 bytes |
| 前端内存 | 整文件常驻（Blob） | 浏览器按缓冲策略管理 |
| 大文件（>50MB） | 基本不可用，JS 堆压力过大 | 无压力 |

### 3. 首字节延迟

| | 方案 A | 方案 B |
|---|---|---|
| 等待 | 整文件读完 + base64 编码 + JSON 序列化 | 浏览器缓冲几秒即开播 |
| 用户体验 | 点击播放 → 长时间等待 → 突然开始 | 点击播放 → 近乎即时开始 |

### 4. HTTP 缓存

| | 方案 A | 方案 B |
|---|---|---|
| 浏览器缓存 | 不支持（Blob URL 无缓存语义） | 标准 HTTP 缓存（304、强缓存） |
| 重复播放同一章 | 每次重新下载全文件 | 命中浏览器缓存，零流量 |

### 5. QuickJS 线程占用

| | 方案 A | 方案 B |
|---|---|---|
| JS 线程 | 阻塞 ±1s（atob 解码大文件） | 无阻塞 |
| 并发能力 | 一次只能处理一个音频请求 | 不经过 QuickJS，宿主 Go 天然并发 |

---

## 安全性考量

方案 B 中宿主直接 serve 文件需要考虑：

- **鉴权**：音频 URL 不应对外暴露，需要挂载插件 token 或短期签名
- **路径穿越防护**：URL 中的文件路径必须校验，防止 `../` 越权读取服务器任意文件
- **范围限制**：仅允许读取插件 data 目录下的文件

这些是宿主（Go 后端）层面的职责，与当前 `songloft.fs` 已有的安全边界一致。

---

## 总结

| 维度 | 方案 A (base64) | 方案 B (宿主 serve) |
|------|:---:|:---:|
| 大文件（>50MB） | 基本不可用 | 无压力 |
| 拖进度条 | 需全量下载完 | 秒拖 |
| QuickJS 内存 | 文件大小的 2-3 倍 | 忽略不计 |
| 首字节延迟 | 等全文件 | 缓冲即播 |
| 浏览器缓存 | 不支持 | 完整支持 |
| 后端改动量 | 已实现 | 需后端加路由 + 鉴权 |
| 前端改动量 | — | 小（Blob URL → http URL） |

**结论**：base64 方案适合小封面、元数据等 KB 级数据。音频文件走这条路是"能跑但走不远"，尤其有声书单章几十 MB、甚至上百 MB 的场景，应该推进方案 B。
